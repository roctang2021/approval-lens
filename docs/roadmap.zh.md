# 开发与发布计划

[English](../ROADMAP.md) · **中文**

更新于 2026-09-05。以下是待开发和待发布的工作，不代表当前已经支持。

Approval Lens 要帮助用户在批准前弄明白：**要做什么、影响哪里、可能发生什么变化。**
接下来围绕解释质量、安装体验和 Claude Code、Codex、Cursor、OpenCode 的审批接入推进。

## 当前起点

**0.29.1 已在 GitHub 公开，可以安装使用。** Claude Code CLI 和真实 Anthropic API
验收已完成，Claude 官方目录正在审核。审批说明支持六种语言；Desktop 和 IDE 界面仍需人工验收。
具体结果见[发布审核记录](release-review.md)。

近期要解决两个差距：本地说明与模型说明会重复；当前 Claude hook 在命中规则时可能增加确认，
还不能给每个原本就会出现的审批补充解释。

## 推进顺序

以下按一名维护者配合 agent 估算，除试用期外均为工作日。版本号是建议；接口限制、
测试用户到位时间和外部审核会影响排期。

| 步骤 | 目标 | 主要交付 | 完成条件 | 预计投入 |
| --- | --- | --- | --- | --- |
| 1 | 完善 0.29.1 发布 | GitHub 直接安装、版本 Release、真实演示、反馈入口 | 新用户能按文档完成安装、找到插件、更新和卸载 | 1–2 天 |
| 2 | 验证审批接入 | Claude 已有审批；优先验证 Codex，再验证 Cursor、OpenCode | 明确文字显示位置、是否增加审批，并选定第二个工具 | 2–3 天 |
| 3 | 0.30：解释更清楚 | 一段简洁说明、可靠回退、简化设置、界面验收 | 不重复；目标和后果清楚；审批行为回归检查通过 | 3–5 天 |
| 4 | 0.31：接入第二个工具 | 一个完整适配器，以及它需要的共享接口 | 第二个工具通过安装和真实审批验收 | 接入验证通过后 5–10 天 |
| 5 | 1.0：稳定支持已承诺范围 | 用户试用、修复、升级说明和发布材料 | 下方发布条件全部满足 | 试用 1–2 周，再按反馈修复 |

第 1、2 步可以交叉进行，文案改进也可以先做；第二个适配器必须先通过接入验证。
官方目录审核单独推进，GitHub 发布和开发无需等审核结束。

## 1. 让当前版本容易安装、容易理解

- README 主安装方式改为已经测通的 GitHub marketplace 命令，ZIP 留作备选。
  修改前，在干净配置下验证首次启动的依赖准备。
- 检查发布提交的 CI，创建 0.29.1 tag 和 GitHub Release。写明已验收的 CLI 范围、
  六种语言、可选 API 费用和当前审批覆盖。官方目录状态在确认上架前保持“审核中”。
- 录制一段真实 CLI 演示，提供前后对比图：原始提示、操作目标、直白解释。
  写磁盘等危险示例只作为分析输入，不实际执行；示意画面明确标注。
- 准备反馈模板，收集工具版本、语言、预期含义和实际说明，提示删除私密信息。
  邀请 5–10 名用户试用，重点了解安装卡点和是否看懂，不自动收集命令或对话。

## 2. 先验证能否出现在正确的位置

每个工具先验证一个待审批操作和一个普通已允许操作，记录工具版本、界面、权限模式、
说明位置、审批次数和用户决定的实际结果。同时检查关闭模型和超时的情况。
这一步用于选择接入方向，不要求完成四个适配器。

| 工具 | 官方文档提供的起点 | 必须验证的问题 |
| --- | --- | --- |
| Claude Code | `PreToolUse`、`PermissionRequest` hooks | 能否给已有审批补充解释，同时不增加确认、不替用户决策？ |
| Codex | 客户端处理 app-server 的审批请求 | 现有 CLI/App 是否提供可用扩展点？如果必须另做客户端，需要多大范围和投入？ |
| Cursor | 执行前 hook 的 `permission`、`user_message` | 说明能否出现在待审批位置，原有权限规则是否保持有效？ |
| OpenCode | v2 权限评估 hook 的决定和消息字段 | 能否只给已有 `ask` 增加说明？哪个已发布版本和界面实际支持？ |

建议跨工具的验证顺序为 **Codex → Cursor → OpenCode**，同时补 Claude 验证。
第二个正式接入选择审批位置可用、安装成本可控的工具。如果 Codex 必须另做客户端，
先记录限制，本轮推进 Cursor 或 OpenCode；Codex 保留在计划中，不宣传为已支持原生 App。

“解释已有审批”模式的验收要求是：测试场景中不增加审批次数、不改变权限决定。
接口不支持时，写明限制，保持当前额外确认行为可见；不能为了显示说明而自动批准或拒绝。

以上是文档提供的验证方向，尚未代表接入成功。来源：
[Claude hooks](https://code.claude.com/docs/en/hooks#permissionrequest)、
[Codex 审批协议](https://learn.chatgpt.com/docs/app-server#approvals)、
[Cursor hooks](https://cursor.com/docs/hooks)、
[OpenCode v2 插件](https://opencode.ai/v2/docs/build/plugins/)。

## 3. 把解释做好

- 显示风险等级、目标和一段简洁说明。具体操作与本地风险信息合并，删除重复后果。
  规则证据和风险等级保持独立，不让模型改写判断。
- 不开模型时，说明本地规则能确认的内容；开启后，在同一位置提供具体解释。
  信息不足就说明不确定；缺少密钥、请求失败或超时，都保留本地解释。
- 审批文字不加“AI 生成”或服务商标签。模型使用方式、费用和发送内容在设置与隐私说明中讲清楚；
  文件内容、任务上下文继续分别征得用户选择。
- 提供设置和检查命令，帮助选择语言、配置模型和排查问题。保留用户已有配置，
  密钥不出现在输出和 shell 历史里。
- 验收已安装的 CLI，以及计划支持的 Desktop/IDE 界面；通过哪个就公布哪个。
  六种语言同步使用新布局。

建立至少 30 个审核场景，包含破坏性修改、数据发送、配置修改、普通操作和上下文不足，
检查目标准确性、误导、重复及截断。六种语言都做显示检查，并邀请熟悉相应语言的用户审阅文案，
如实记录哪些语言已经完成语言审阅。

分别测本地解释和真实模型的耗时。初始目标：记录的测试环境中，本地热启动 p95 低于 300 毫秒，
模型 p95 低于 4 秒；达到配置的模型时限即回退。这些是待验证目标，报告时注明样本量、
首次启动开销和实际结果，不作为性能保证。

## 4. 完整接入第二个工具

在适配器入口统一操作类型、命令或目标、可用上下文和工具能力，复用解析、规则及语言文本。
宿主对话读取、显示、模型请求和本地存储分别通过明确接口接入，先抽出两个工具确实需要的部分。

验收支持的操作、允许列表、已拒绝操作、批准与拒绝、无人值守、取消、并发请求和模型故障。
解释必须对应当前待审批的那项操作。重新运行 Claude 回归测试，为新工具写好安装、升级、卸载
和未支持界面，再宣布支持。

## 5. 什么时候发布 1.0

1.0 按承诺的体验是否稳定来判断，不要求四个工具全部完成。此前的版本仍可通过 GitHub Release
和官方目录分发；1.0 表示我们对已公布范围的维护和兼容性作出更明确的承诺。

- 宣传支持的工具和界面全部通过对应自动检查及真实审批验收。
- 没有已知问题会反转用户决定、隐藏待审批操作，或在审核场景中给出实质性误导。
- 试用目标：至少 5 人中的 4 人无需维护者介入即可安装，并在三个示例审批中正确说出操作和目标。
- 升级和卸载通过；发布说明包含配置变化、限制及可回退的旧版本。
- README、演示、隐私说明和 marketplace 描述与发布版本一致。
  每周查看目录提交状态，收到补充要求时处理，避免重复提交。审核时间由 Anthropic 决定，
  [官方指南](https://claude.com/docs/plugins/submit)没有固定时限。

代码、测试、文档和发布准备可由 agent 协助执行；维护者负责范围决策和邀请测试用户，
试用用户提供理解反馈，Anthropic 决定是否上架。

## 后续范围

继续用同样的验证和验收流程接入剩余的 Codex、Cursor、OpenCode。工具接入与模型服务商接入
分别推进；早期用户确有需求时，再优先增加 OpenAI 兼容或企业统一管理的模型端点，并验证数据处理与回退。

托管后台、SSO、计费、独立网站或域名、更多语言暂缓，等需求足以支撑维护成本再做。
近期主要看用户能否顺利安装，以及能否看懂审批。
